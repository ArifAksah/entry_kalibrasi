# Taste
- Communicates in Indonesian (Bahasa Indonesia) and expects replies in Indonesian. Confidence: 0.7
- Writes in casual, informal Indonesian (e.g., uses "lu", short unpunctuated run-on phrasing when reporting issues) — a relaxed, direct tone fits better than formal/procedural language. Confidence: 0.55
- Wants the agent to trace and verify data lineage before changing anything — confirm where a field's value comes from and which flow actually consumes it, and flag values that "point nowhere" (orphaned/mis-wired), rather than just filling a value in. Diagnosis-first with evidence from the real DB/code; when reporting that data they entered doesn't appear, expects the agent to check FIRST whether it was actually persisted vs merely failing to render ("tolong kamu cek ini dulu") instead of jumping to a code edit. Confidence: 0.55
- Asks for the agent's opinion/recommendation before making ambiguous design or UX calls rather than having the agent decide unilaterally (e.g., "aku ingin mendengar pendapat kamu dulu"), and wants the advice tailored to the specific feature/domain at hand rather than generic solutions. Confidence: 0.6
- Pragmatic about dev-time data: explicitly OK with dummy/placeholder values (e.g., dummy certificate numbers) while a feature is still in development — doesn't require real, production-quality data to unblock progress. Confidence: 0.5
- Willing to delegate implementation fully and trusts the agent's approach — grants the agent latitude to pick the implementation approach ("saya kasih kepercayaan kamu pendekatan mana yang kamu mau, apakah kamu enkakuplasi atau bagaimana") and once a plan/recommendation is presented prefers the agent to proceed autonomously through the multi-step change rather than seeking repeated per-step confirmation. Confidence: 0.6
- Treats the project's Excel "FORMAT ..." workbooks as the authoritative spec for calibration procedure and formulas — expects the app's UI/inputs and calculations to match the workbook's sheet layout (same headers, set points, and columns) AND its computed numeric results, treating any mismatch between the app's figures (uc, k, U95, etc.) and the workbook as a bug to reconcile rather than an acceptable approximation. Explicitly asks whether the UI "already implements" what the workbook does (e.g., "jika kita merujuk ke desain yang ada di excel"). When the code's method is more mathematically sophisticated/correct than the workbook (e.g., its circular/vector mean for wind direction vs the workbook's plain arithmetic AVERAGE), still prefers fidelity to the workbook's simpler method — pick the workbook-matching computation over the "better" one. Confidence: 0.75
- Wants changes scoped strictly to the broken/incomplete part and expects working code to be left untouched — will explicitly say the other parts are already correct ("yang lain itu udah benar, jangan sentuh yang lain") and only the affected module (e.g., tipping bucket) should be changed, judging a fix by whether it leaves the correct paths unaffected. Confidence: 0.65
- Prefers reusing an existing display format/convention as-is ("ikut format aja") instead of inventing new fields or columns — when a surface already follows a pattern (e.g., "nama/merk/tipe/SN"), keep it consistent rather than enriching the layout. Confidence: 0.5
- Cares about cross-surface UI consistency and completeness: when the same data appears in multiple places it should match everywhere, and surfaces that show only partial or misleading info are flagged as "aneh sendiri" and expected to be made consistent or removed rather than left as-is. Confidence: 0.55
- Wants a new/variant view rendered with the SAME table design as the canonical one so everything looks uniform in the same surface — when a new panel/component is introduced next to an existing one, expect it to replicate the existing table's columns, headers, summary rows, and styling rather than using its own (e.g., card-style) component design, even when the underlying data differs. Confidence: 0.6
- Expects relationship/assignment data in the app to be FUNCTIONAL, not cosmetic: assigning multiple users to an entity (e.g., picking several "petugas kalibrasi" on a calibration order) should form a real team that shares access and can each work on that entity's records, not merely register names. Still wants strict scoping — users may only view/edit what they created or were explicitly assigned to, and everything else must remain inaccessible ("hanya project yang mereka kerjakan aja yang bisa diubah; yang ga dia buat dan ga di-assign tetap gabisa"). Team-based shared access with strict project scoping. Confidence: 0.55
- Distinguishes collection-list visibility from single-record access: index/list endpoints should be scoped so a non-admin only sees records they created or were explicitly assigned to, while opening an individual record (its detail view) may stay available to every member of the relevant role (e.g., all calibrators can open any calibration order's detail). Applies the same scoping consistently to every list surface that can feed downstream work (e.g., the per-station order picker used by the certificate form), so an unassigned order can't be selected to create/edit a certificate. Confidence: 0.6
- Prioritizes security/audit posture over convenience: wants records isolated ("lebih aman dan isolate"), original document integrity preserved, clear authorship tracking ("bisa di tracking siapa pembuatnya"), and no loopholes for anyone outside the permitted team to view or manipulate others' records — accepts stricter/tighter access even if it means some users lose visibility, and expects enforcement at BOTH the server (authoritative checks) and the UI (hide actions a user isn't allowed to take so they never even see the button). Confidence: 0.6
- Prioritizes readability/contrast in UI text: dislikes muted gray text that is "susah di baca" and explicitly asks for plain black text on light surfaces, judging a UI by whether the content is easy to read at a glance. Confidence: 0.6
- Dislikes cramped/small form fields and expects inputs to be comfortable to use — prefers larger, full-width fields (own row, generous padding/height) over small inline controls squeezed next to a label or header, and calls out field size as a UX problem rather than a cosmetic nit. Confidence: 0.55
- Favors lean, minimal UI surfaces: flags informational panels/cards as "redundan" and "over information" and asks for them to be deleted outright, especially when they merely restate data the user already knows or values that are locked/read-only elsewhere (e.g., removing a "Sumber Data: Order Kalibrasi" box showing No. Order / No. Identifikasi / Kode Alat from a certificate form). Prefers the agent to strip the clutter rather than keep explanatory/placeholder text. Confidence: 0.6
- Evaluates UI by interaction friction and treats overlay/menu content getting clipped by a scrollable container — so the user must scroll just to see the options — as a genuine UX problem ("kurang ramah UXnya"), not a cosmetic nit. Expects a robust interaction pattern where menus/overlays always render fully visible regardless of the parent container's `overflow` (e.g., rendering the menu via a portal with viewport-bounded height and auto-flip so it needs no scrolling). Confidence: 0.5
- Treats the parent/booking record as the single source of truth for derived child records: when a document (e.g., a certificate) originates from an order, fields that describe the same thing (e.g., calibration session date range) should be sourced from the order's own fields rather than re-entered, so the two surfaces can never drift apart. Confidence: 0.6
- Prefers defaults over guard rails in forms: derived fields should be PREFILLED from the parent record as a convenience default, but left editable — rejects making them read-only/locked. Once the user has entered/changed a value, the prefill must not overwrite it, so staff can freely override when reality differs and otherwise just continue filling the rest. Prefers non-blocking, non-enforcing UX over restriction. Confidence: 0.7
- When asking which method/approach is "correct", wants the answer grounded in the actual raw data of the specific record at hand — query the real data and compute/quote its distribution (counts, min/max, per-segment grouping, derived stats like a vector resultant) before generalizing. Textbook/statistical-theory answers ("in theory circular mean is right") miss the point; the user will steer the agent back with "maksud gw dari pertimbangan raw data". Confidence: 0.5
- Prefers fixing root causes at the schema/database layer over code-level workarounds: when data fails to appear because a foreign key is missing, expects the agent to add the FK in the DB (directly, e.g. via the local Supabase docker/`docker exec ... psql`) rather than compensating with manual joins in application code, and will call this out as "pendekatan yang lebih baik". Trusts the agent to reach into the local DB container directly and still wants the change recorded as an idempotent, reproducible migration file. Confidence: 0.6
- On broken-data / database repair tasks (e.g. login failing due to mismatched ids), prefers the agent to just go ahead and apply the fix on the backend ("kamu masuk dan lakukan perbaikan di sisi supabase jika itu diperlukan") instead of pausing to ask permission first — once the root cause is established, expects direct action on the DB rather than a confirmation prompt. Autonomy here is scoped to data/infra repairs, not to design/UX decisions (those should still be discussed). Confidence: 0.55
- Expects the whole class of affected entities to be fixed and verified, not just the one reported: when one account/record is broken, wants the agent to sweep the rest ("pastikan semua akun bisa login") and report the verified end state for each of them rather than only the original case. Confidence: 0.5
- Expects post-change parity checks across every related sensor/system, especially when both surfaces consume the same standard and UUT data: after aligning a formula, recompute or compare all affected instruments rather than validating only the originally reported mismatch. Confidence: 0.7
- Treats small numerical differences in calibration results as serious, NOT dismissible: when app vs workbook/SIMKAL values differ even slightly, expects the agent to quantify exactly how small (order of magnitude) and root-cause whether it comes from differing precision/scale of the stored raw inputs (e.g., decimal/comma representation of entered data) versus floating-point rounding in the arithmetic — an explicit "it's just floating point" hand-wave is rejected because the system performs instrument calibration. Wants precise attribution of the delta, not reassurance ("apakah karena raw data yang masuk memiliki nilai koma yang berbeda atau ini disebabkan oleh floating point... perbeda kecil itu gabisa di anggap sepele"). Confidence: 0.65
- Expects domain-specific variants to be modeled and surfaced explicitly rather than folded into a generic single-value path — e.g., when a calibration genuinely uses two standard instruments, both standards' identity and all their per-instrument metadata (traceability "tertelusur ke SI", reference document / standard certificate number) must be captured per standard and rendered across every surface (CRUD, certificate view, PDF), not collapsed into one "general/single standard" field. They will push back when a per-instrument field is presented as a single setup-level input. Confidence: 0.55
- Separates investigation/analysis from implementation and expects the agent to respect it: when asking the agent to inspect something ("saya hanya ingin melakukan test dan analisis"), explicitly says NOT to change anything yet ("kamu ga usah ubah dulu") — report findings and hold off edits even if a problem is found, rather than jumping straight to a fix. Confidence: 0.6
- Wants the underlying domain process understood before adjusting logic: even as a non-expert, wants to know how the real practitioner treats the data and formulas so that a future formula change can be referenced back to that ground truth. Confidence: 0.5
- Expects access/visibility to be scoped in ONE authoritative place (the server/query) and wants the UI to simply reflect it — neither exposing actions a user may not take nor (as here) hiding records the user is entitled to see. Treats redundant client-side re-filtering that disagrees with the server's authorization as the bug to remove, not something to patch; when a user "should have access" but a record doesn't show, expects the fix to be removing the stale client filter so the UI matches server scope. Confidence: 0.5
- Works against a locally running dev server and reports defects by naming the affected page/feature (often with its localhost URL) and asking for an immediate fix ("...tolong kamu perbaiki itu dulu"); expects the agent to reproduce the problem on the real running system (e.g., log in as the affected role and call the endpoints), explain the root cause, and then apply the fix, treating that fix as the immediate priority. Confidence: 0.5
